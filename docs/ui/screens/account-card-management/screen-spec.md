# SCR-050 계좌·카드 정보 관리 — 화면군

Status: DRAFT

마지막 수정: 2026-10-05, KST

기능 문서: [계좌·카드 관리](../../../features/account-card-management.md)

기존 제품 문서: [SCR-050](../../../product/screens/SCR-050-account-card-management.md)

업로드 안내: [화면별 이미지 경로](./README.md)

## 문서 상태와 적용 범위

이 문서는 기존 단일 관리 화면을 6개 화면으로 세분화한 **설명 초안**이다. 사용자와 대화에서 합의한 화면 구성 변경을 기록하되 미정 데이터 계약·필수 입력·실제 구현까지 승인된 것으로 간주하지 않는다.

기존 이 문서의 `Status: APPROVED`와 루트 `reference.png`는 이전 통합 시안의 승인 이력이다. 이미지 파일은 변경·삭제하지 않고 보존한다. 이전 시안의 명의 선택, 결제계좌 연결, Drawer/Modal 중심 배치를 이번 화면군의 최신 확정 요구사항으로 재적용하지 않는다.

새 화면별 이미지는 각 하위 폴더의 `reference.png`로 업로드할 예정이며 **현재는 이미지 업로드 대기 상태**다. 이미지 업로드·정합성 검토·디자인 승인·구현 검증은 각각 별도로 기록한다. 기존 이미지가 존재한다는 이유만으로 하위 화면을 APPROVED로 표시하지 않는다.

## 화면 목적과 책임

사용자가 계좌와 카드를 등록·조회·수정·비활성화하고, 다른 기능에서 동일한 금융수단 식별자를 참조할 수 있도록 기준정보를 관리한다. 계좌 자체와 실제 현금·보유자산·평가액은 구분한다. 등록·수정만으로 입출금·매매·카드 거래·현금잔고를 생성하거나 변경하지 않는다.

금융기관/카드사 목록 선택은 개인 계좌·카드의 실제 존재·명의·사용 가능 여부를 조회하는 금융 연동이 아니다. 투자·거래에서 같은 금융수단을 참조한다는 관계는 이 상세 화면에 활용현황 집계가 있어야 한다는 뜻이 아니다.

## 화면 구성과 문서 위치

하나의 상위 메뉴와 계좌/카드 탭을 유지하고 목록·상세·등록/수정의 설명과 이미지를 분리한다. 아래 하위 ID는 문서 식별자이며 실제 route/API 경로 확정을 의미하지 않는다.

| ID | 화면 | 설명 초안 | 이미지 예정 경로 |
| --- | --- | --- | --- |
| SCR-050-01 | 계좌 목록 | [account-list](./account-list/screen-spec.md) | `account-list/reference.png` |
| SCR-050-02 | 계좌 상세 | [account-detail](./account-detail/screen-spec.md) | `account-detail/reference.png` |
| SCR-050-03 | 계좌 등록·수정 | [account-form](./account-form/screen-spec.md) | `account-form/reference.png` |
| SCR-050-04 | 카드 목록 | [card-list](./card-list/screen-spec.md) | `card-list/reference.png` |
| SCR-050-05 | 카드 상세 | [card-detail](./card-detail/screen-spec.md) | `card-detail/reference.png` |
| SCR-050-06 | 카드 등록·수정 | [card-form](./card-form/screen-spec.md) | `card-form/reference.png` |

```text
계좌·카드 정보 관리
  계좌 탭 → 계좌 목록 → 계좌 상세 → 계좌 수정
                     → 계좌 등록
  카드 탭 → 카드 목록 → 카드 상세 → 카드 수정
                     → 카드 등록
```

상세와 등록/수정은 Desktop/Mobile 각각 독립된 화면 단위로 정의한다. 등록과 수정은 같은 폼의 모드로 관리한다. 기존 Drawer/Modal의 필수 사용 조건은 유지하지 않으며 실제 URL은 구현 전에 확정한다.

## 이번 대화에서 확정한 화면 방향

| 항목 | 반영 내용 |
| --- | --- |
| 기본 톤 | 첨부된 차곡 시안의 흰 배경, 연한 경계선, 녹색 주요 액션, 민트색 선택/상태 표시를 유지한다. |
| 명의 설정 | 명의 입력·선택 UI를 제거한다. 등록은 로그인 사용자 명의이며 다른 구성원으로 변경할 수 없다. |
| 카드 연결계좌 | 결제계좌·연결계좌 입력·표시·변경과 매핑 의존성을 이번 화면군에서 제외한다. 카드 등록에 계좌 등록을 선행 요구하지 않는다. |
| 활용현황 | 자동이체 사용, 목표 자금, 기타 참조, 사용 중 N개 등 집계 영역을 제외한다. |
| 상세 사용상태 | 상태는 상단 배지 한 곳에 표시한다. 중복되는 하단 사용상태 탭·카드·행은 제외한다. |
| 웹 상세 블록 | 상단 요약과 본문 기본정보를 하나의 상세 카드로 통합한다. |
| 상세 상단 버튼 | 상단 수정 및 설정/더보기 버튼을 제거한다. |
| 상세 하단 액션 | 목록으로·비활성화·수정을 기본으로 한다. 수정·비활성화는 본인 권한에 따라 노출한다. |
| 관리 단위 | 계좌·카드는 하나의 메뉴 안에서 탭으로 관리하고 6개 하위 화면으로 문서화한다. |

명의 설정 제거는 가계 구성원 조회 정책을 폐기한다는 뜻이 아니다. 가계 전체 목록의 구성원 필터나 읽기 전용 소유자 표시는 필요에 따라 유지할 수 있다. 사용자를 바꿔 조회하거나 수정 화면을 열었다는 이유로 기존 소유자를 현재 로그인 사용자로 덮어쓰지 않는다.

## Design Reference / Responsive

현재 하위 화면의 `reference.png`는 Desktop/Mobile 결합 보드를 위한 업로드 위치다. 추가로 뷰포트별 파일이 준비되면 `reference-desktop.png`, `reference-mobile.png`를 사용할 수 있다. 실제 존재하지 않는 파일을 이미지 링크로 삽입하거나 같은 결합 보드를 이름만 바꿔 분리본처럼 취급하지 않는다.

Desktop 목록은 사이드바·탭·검색·필터·테이블을 사용하고 Mobile 목록은 카드형 목록과 축약 검색·필터를 사용한다. 상세는 하나의 정보 영역, 폼은 입력 영역과 하단 액션으로 구성한다. 두 뷰포트의 기능·권한·검증은 동일하며 배치만 조정한다. 실제 캔버스 규격과 접근성·반응형 검증은 후속 작업이다.

이 화면군에서 루트 `reference.png`는 이전 통합 참고 이미지다. 새 하위 이미지의 정합성 검토가 끝나기 전에는 이를 최종 시각 계약으로 승격하지 않는다. 이미지와 명시된 사용자 합의가 다르면 합의된 제거·통합 방향을 유지하고 이미지 보정 사항을 기록한다.

## 공통 권한과 생명주기

- 같은 가계의 조회 가능 범위에서 다른 구성원의 금융수단을 조회할 수 있다. 일반 사용자의 등록·수정·비활성화는 본인 명의에 한정한다.
- 등록 소유자는 인증된 로그인 사용자로 결정하고 수정 시 기존 소유자를 유지한다. 프론트 버튼 숨김만으로 인가를 대체하지 않는다.
- 비활성화는 확인 후 수행하며 물리 삭제하지 않는다. 신규 거래·투자 입력 선택에서는 제외하고 과거 거래·투자·카드실적 참조는 유지한다.
- 비활성화가 자산 총액에서 잔액을 무조건 제외한다는 뜻은 아니다. 잔액·평가액 집계 정책을 별도로 정의한다.
- 재활성화, 비활성 금융수단의 기본정보 수정 범위, 가계 이동·탈퇴·명의 이전 등은 후속 확정한다. 상태 라디오만으로 이 정책을 암묵적으로 추가하지 않는다.
- 계좌·카드의 사용상태와 외부 금융 연동 상태는 구분한다. 연동 오류를 비활성화나 삭제로 처리하지 않는다. 초기 화면에 연계대기 상태를 필수로 추가하지 않는다.

## 공통 상태와 사용자 결과

| 상태 | 사용자 결과 |
| --- | --- |
| Loading | 불러오는 중임을 알린다. 미확인 건수·금액을 실제 0처럼 표시하지 않는다. |
| Empty | 등록 정보가 없다는 안내와 본인 금융수단 등록 진입점을 제공한다. |
| No Result | 검색·필터 결과가 없다는 안내와 조건 초기화를 제공한다. |
| Error | 원인을 이해할 수 있는 안내와 재시도를 제공한다. 검색·폼 입력은 가능한 범위에서 보존한다. |
| Permission Denied / Not Found | 접근 불가 또는 대상 없음으로 안내하고 허용된 목록으로 복귀할 수 있게 한다. |
| 저장·비활성화 처리 중 | 중복 제출을 막고 실제 성공 전 완료로 표시하지 않는다. |
| 동시 수정·권한 변경·중복 충돌 | 성공한 것처럼 덮어쓰지 않고 최신 상태 확인과 입력 보존 정책을 적용한다. |

입력 실패 시 보존, 조건 변경 시 목록 갱신, 상세에서 목록 복귀, 미저장 변경 폐기 확인 등은 화면별 표의 초안 방향을 따른다. 실제 구현 계약과 검증은 별도다.

## 금융기관·번호 입력 정책

금융기관과 카드사 선택은 내부에서 제공하는 검증된 목록을 사용한다. 사용자가 등록할 때마다 공공 API를 직접 호출해야 한다고 가정하지 않는다. 목록 로딩·검색 결과 없음·초기 목록 미확보·기존 목록 사용을 구분하고, 출처 기준년월과 실제 수집시각을 구분한다. 목록에 없는 기관의 처리 방식과 최종 공급자·갱신 방식은 기능 문서의 미정 사항을 따른다.

번호 검증은 확정된 입력 형식 검사에 한정한다. 실제 존재·명의·사용 가능 여부 확인으로 표시하지 않는다. 계좌번호·카드번호의 전체 저장 필요성, 허용 문자·길이·하이픈 처리, 기관별 규칙, 중복 판단·마스킹·로그 차단은 후속 상세 계약에서 확정한다. 비밀번호·CVC·인증코드는 이 기능의 입력 대상이 아니다.

수정 화면의 마스킹값을 실제 번호로 저장하지 않는다. 원본 조회 없이 수정하는 정책을 선택한 경우 기존 번호 유지와 번호 변경을 구분한다.

## 시안에 보이지만 아직 확정하지 않은 항목

| 항목 | 초안 처리 |
| --- | --- |
| 총 잔액·현재 잔액 | 조회값의 출처·기준시점·통화·중복 합산 정책 확정 후 표시한다. 미확인을 0으로 채우지 않는다. |
| 등록/수정의 현재 잔액 입력 | 계좌 기준정보와 실제 현금 상태의 책임을 먼저 분리한다. 이 폼 저장으로 잔액을 변경하지 않는다. |
| 이번 달 카드 사용액·전월 대비 | 거래 범위·기준월·취소 처리·집계 기준 확정 후 제공한다. |
| 계좌/카드 유형 비중 | 유형 코드와 집계 기준 확정 후 제공한다. 시안의 비율·유형 이름을 확정 계약으로 취급하지 않는다. |
| 개설일·결제일·월 실적 기준 | 필수 여부, 카드유형별 적용 및 다른 기능과의 책임을 후속 확정한다. |
| 통장 용도, 카드 유효기간·발급일·연회비·혜택 | 분리 시안에서 추가된 미합의 항목이다. 자동으로 기능 범위나 저장 모델에 추가하지 않는다. |
| 필수 별표·글자수·자동 하이픈 | 이미지의 임의 표기를 검증 규칙으로 확정하지 않는다. |
| 상태 직접 전환 | 신규 기본값·비활성화 확인·재활성화 정책과 함께 결정한다. |

분리 시안에서 카드 목록의 “계좌 등록” 버튼은 “카드 등록”으로 보정해야 한다. 전체 번호 표시·상단 추가 액션·미합의 필드 등 이미지와 본문 차이는 업로드 후 시안 보정 목록으로 관리한다.

## Data / API Dependency

필수 개념은 계좌/카드 목록·상세·등록·수정·비활성화, 금융기관/카드사와 유형 기준정보, 인증된 사용자·가계 조회/변경 권한이다. 투자 기능에서는 동일한 계좌 식별자를 재사용하고 별도 계좌를 중복 생성하지 않는다.

카드 결제계좌 매핑, 활용현황 집계, 카드 상품·혜택 자동조회, 실시간 금융 연동은 이번 화면군의 필수 의존성이 아니다. endpoint, 요청·응답 모델, DB 스키마, 기관 코드, 충돌·중복 처리 방식은 이 문서로 확정하지 않는다.

## 기존 문서와의 차이 및 후속 동기화

기능 문서와 기존 제품 문서에는 결제계좌, 명의 입력 후보, Drawer/Modal, 연결 정보 등 이전 정의가 남아 있다. 이번 변경에서는 사용자가 지정한 UI 화면군과 이미지 경로를 중심으로 초안을 추가하고, 상위 UI 안내의 이전 이미지 우선순위만 최소 보완한다.

**계좌·카드 화면군에서는 위 사용자 확정 변경을 적용한다.** 기능·제품 문서의 관련 문구, API/모델이 존재하는 경우 그 계약의 동기화는 후속 작업으로 남긴다. 이 초안으로 기존 API·DB가 이미 바뀌었다고 표시하지 않는다.

## Acceptance Criteria

- [ ] 6개 화면의 설명과 이미지가 각각 대응하고 하위 문서에서 공통 문서로 이동할 수 있다.
- [ ] 명의 입력·결제계좌·활용현황·중복 상태/상단 액션이 제거된 방향으로 구현된다.

- [ ] 조회·변경 권한, 비활성화 및 과거 참조 보존이 검증된다.
