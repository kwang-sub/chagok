# SCR-050-03 계좌 등록·수정

현재 구현 범위: t_8a3ca453 승인 CODE_DRIVEN 샘플 UI. 아래 v2 계약이 이번 구현 기준이다. 기존 본문의 실제 저장/인가·필수/형식 검증·중복/충돌 정책은 후속 초안으로 보존하고 구현 완료로 표시하지 않는다. 디자인은 DRAFT다. 입력 확인은 저장이 아니다.

Status: DRAFT

마지막 수정: 2026-10-14, KST

상위 명세: [계좌·카드 화면군](../screen-spec.md)

이미지 업로드 방법: [화면별 이미지 안내](../README.md)

## 화면 목적

본인 명의 계좌의 기본정보를 등록하거나 기존 계좌 정보를 수정한다. 로그인 사용자의 명의로 등록하므로 명의를 따로 선택하거나 입력하지 않는다. 계좌 등록·수정이 실제 입금·출금·매매 또는 현금잔고 변경을 발생시키지 않는다.

## Design Reference / Viewport

기존 차곡의 흰색·녹색·민트 톤을 유지한다. Desktop은 공통 사이드바와 하나의 입력 카드, Mobile은 별도 세로 입력 화면을 사용한다. 폼 하단에 취소·저장을 배치한다. 입력 화면 상단에 또 다른 계좌 등록 버튼이나 설정/더보기 액션을 넣지 않는다.

등록과 수정은 같은 폼 구성을 재사용하되 제목, 초기값, 저장 후 돌아갈 위치를 구분한다. 별도의 다단계 가입이나 계좌 인증 절차는 추가하지 않는다.

## 입력 항목 초안

아래 표는 화면에서 다룰 후보와 검증 방향이다. 이미지의 별표나 예시값만으로 필수 여부·길이·정규식·저장 범위를 확정하지 않는다.

| 항목 | UI | 초안 및 주의사항 |
| --- | --- | --- |
| 계좌명 | 텍스트 입력 | 사용자가 알아보기 쉬운 이름. 필수 제안이며 최대 길이·중복 이름 허용 정책은 후속 확정한다. |
| 금융기관 | 검색 가능한 선택 UI | 검증된 기관 기준정보에서 선택한다. 기관명 자유 입력으로 공통 목록을 변경하지 않는다. 필수 제안이다. |
| 계좌유형 | 선택 UI | 지원 유형 기준정보를 사용한다. 기관 분류·계좌 용도·연금/ISA 제도 구분의 코드 체계는 미정이다. |
| 계좌 식별정보 | 번호 입력 후보 | 형식 검사만 수행하며 실제 존재·명의 일치 확인으로 표시하지 않는다. 전체 번호 필요성·저장 여부·필수 여부는 후속 확정한다. |
| 개설일 | 날짜 입력 후보 | 선택 입력을 기본 제안한다. 시안에 필수 표시가 있더라도 확정 정책으로 취급하지 않는다. |
| 메모 | 여러 줄 입력 | 선택 입력. 길이 제한과 카운터의 기준은 후속 확정한다. |
| 사용상태 | 상태 표시/전환 후보 | 신규 계좌는 사용중을 기본으로 하는 방향을 제안한다. 상세의 비활성화 확인 흐름과 중복되지 않게 하며 재활성화 정책을 암묵적으로 추가하지 않는다. |

명의 입력·선택은 제공하지 않는다. 등록 시 소유자는 인증된 로그인 사용자로 결정하고, 수정 시에는 기존 소유자를 유지한다. 화면에서 명의를 숨기는 것만으로 인가를 대체하지 않는다.

시안의 현재 잔액 입력은 책임 분리 검토 대상이다. 기본정보 저장 요청에 현재 잔액을 섞어 임의로 자산·현금 상태를 변경하지 않는다. 기준일 초기잔고 입력을 제공하려면 별도 계약을 먼저 확정해야 한다.

## 번호 입력과 민감정보

번호의 허용 문자·길이·공백·하이픈 정규화는 후속 상세 계약에서 정한다. 이미지의 “하이픈 자동 삽입” 안내는 구현 확정이 아니다. 형식 통과 문구는 “입력 형식이 올바릅니다” 수준으로 제한하고 “계좌 인증 완료”라고 표현하지 않는다.

수정 화면에서 원본 번호를 제공하지 않는 정책을 선택한 경우, 기존 번호 유지와 새 번호 변경을 구분해야 한다. 마스킹된 값을 검증 오류로 만들거나 필수 입력이라며 전체 번호를 매번 다시 요구하지 않는다. 구체적인 번호 변경 허용 범위는 저장 정책과 함께 확정한다. 번호·인증정보를 URL, 오류 메시지, 로그에 그대로 남기지 않는다. 비밀번호·인증코드 등은 입력 대상이 아니다.

## Responsive / Data Dependency

Desktop과 Mobile의 입력 필드·검증·권한은 같다. Mobile은 폼이 스크롤되더라도 오류 위치와 취소·저장 버튼에 접근할 수 있어야 한다. 기관 목록의 키보드 검색과 선택, 필드 라벨과 오류 연결을 고려한다.

계좌 생성·수정·상세 읽기, 금융기관·계좌유형 기준정보, 로그인 사용자 권한이 필요하다. 실제 endpoint, 필수 필드, 중복 판정, 번호 저장, 동시 수정 방식은 구현 전 확정한다. 잔액·거래 생성이나 활용현황 집계 API는 이 폼의 필수 의존성이 아니다.

## Acceptance Criteria

- [ ] 등록·수정 제목, 초기값, 취소·저장 후 이동이 구분된다.
- [ ] 명의 입력 UI가 없고 인증된 본인 소유권을 서버에서 검증한다.
- [ ] 기관 검색의 로딩·검색 결과 없음·오류·기존 목록 사용 상태를 구분한다.
- [ ] 형식 확인을 금융사 실명·존재 확인으로 오인하게 하지 않는다.
- [ ] 실패·충돌 시 입력 보존과 중복 제출 방지가 동작한다.
- [ ] 마스킹값을 실제 번호로 재저장하지 않는다.
- [ ] 기본정보 저장이 잔액·입출금·매매를 변경하지 않는다.

위 항목은 이전 전체 제품 초안의 기준이다. 이번 샘플 구현의 동작/검증 범위는 아래 v2 계약과 run별 증적으로 구분하며 전체 제품 완료를 의미하지 않는다.
