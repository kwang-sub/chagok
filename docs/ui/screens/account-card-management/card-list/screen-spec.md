## 화면 목적

등록된 카드를 조회·검색·필터링하고 카드 상세 또는 등록 화면으로 이동한다. 계좌와 같은 상위 메뉴를 사용하지만 카드 기준정보를 독립적으로 관리한다. 카드 사용내역 입력, 혜택 분석, 결제계좌 연결은 이 목록의 기능이 아니다.

## Design Reference / Viewport

흰 배경, 연한 경계선, 녹색 액션과 민트색 선택·상태 표시를 사용한다. Desktop은 공통 사이드바와 테이블, Mobile은 카드형 목록을 사용한다. 계좌 목록과 탭·요약·검색·필터 위치를 일관되게 유지하되 카드사·카드유형 등 카드 전용 정보를 표시한다.

분리 시안에 카드 탭의 등록 버튼이 “계좌 등록”으로 표시된 부분은 오기다. 이 화면에서는 Desktop/Mobile 모두 **카드 등록**으로 표시해야 한다.

## 화면 구성

| 영역 | 노출 UI | 설명 |
| --- | --- | --- |
| 제목 | 계좌·카드 정보 관리, 카드 등록 | 현재 탭은 카드이며 등록 동작도 카드 폼을 연다. |
| 탭 | 계좌 / 카드 | 카드 탭을 선택 상태로 표시한다. |
| 요약 | 카드 수, 사용중/비활성 수 | 가계·구성원 조회 범위에 따른 등록 현황이다. 검색 결과 건수와 구분한다. |
| 집계 후보 | 이번 달 사용액, 전월 대비, 카드 종류 비중 | 사용액의 거래 출처·기간·취소 반영 기준과 유형 코드가 확정된 뒤 제공한다. 카드 수만으로 사용액을 계산하지 않는다. |
| 필터 | 카드사, 카드유형, 구성원, 사용상태 | 구성원은 조회 필터다. 명의 입력·변경과 다르다. |
| 검색 | 카드명·카드사 검색 | 번호 검색 범위는 민감정보 정책 확정 후 결정한다. |
| 목록 | 카드명, 카드사, 카드유형, 마스킹 식별정보, 결제일 후보, 사용상태 | 가계 전체 조회 시 소유자 구분은 읽기 전용으로 제공할 수 있다. |
| 금액 후보 | 이번 달 사용액 | 집계 계약이 확정된 조회값만 표시한다. 미확인 값은 0으로 채우지 않는다. |
| 목록 이동 | 검색 결과 건수, 페이지 이동 | 정렬·페이지 크기의 구체값은 후속 확정한다. |

카드 결제계좌·연결계좌 열, 연결 여부 배지, 활용현황·참조 건수는 제공하지 않는다. 카드 상품 이미지와 로고가 없으면 공통 아이콘을 사용한다. 실제 카드 상품·혜택 자동조회가 가능하다고 가정하지 않는다.

| 재조회 | 새로고침 또는 오류 재시도 | 현재 조건으로 목록 재조회 | 금융사 실시간 거래 동기화를 실행하는 버튼으로 설명하지 않는다. |
| 페이지 이동 | 페이지 제어 선택 | 조건을 유지하고 결과 페이지 변경 | 상세에서 돌아올 때 조회 맥락을 복원하는 방향을 따른다. |

목록의 수정 바로가기는 추가 노출 후보이며 기본 편집 경로는 상세 하단 수정이다. 노출할 경우 본인 카드에서만 동일한 수정 화면으로 연결한다.

## Responsive / Permission

Desktop은 테이블을 사용하고 Mobile은 카드명·카드사·유형·상태를 우선하는 카드형 목록을 사용한다. 검색·필터는 Mobile에서도 사용할 수 있어야 한다. 상단 추가 버튼과 FAB의 동시 노출 여부는 중복 등록 진입점을 검토해 확정한다.

다른 구성원 카드의 조회를 허용하더라도 등록·수정·비활성화는 본인 명의에 한정한다. 명의 입력을 제거해도 가계 조회 범위와 변경 권한을 함께 제거하지 않는다.

## 상태와 예외

| 상태 | 화면 결과 |
| --- | --- |
| Loading | 로딩을 표시하고 집계값을 임의의 0으로 채우지 않는다. |
| Empty | 등록된 카드가 없다는 안내와 카드 등록 진입점 제공. 계좌 등록을 선행 조건으로 안내하지 않는다. |
| No Result | 조건에 맞는 카드가 없다는 안내와 조건 초기화 제공. |
| Error | 검색·필터를 보존하고 재시도 제공. |
| Permission Denied | 허용되지 않은 가계 카드 정보를 노출하지 않고 접근 제한 안내. |
| 비활성 카드 | 상태를 구분해 조회 가능. 신규 거래 선택에서는 제외하되 기존 거래·실적 참조는 유지. |

카드 사용액 집계가 아직 없더라도 카드 목록·등록·상세의 기준정보 기능은 독립적으로 사용할 수 있는 방향으로 설계한다.

## Data / API Dependency

카드 목록과 상태, 카드사·카드유형 기준정보, 가계 조회 권한, 로그인 사용자 정보가 필요하다. 이번 달 사용액·전월 대비는 거래 집계 계약이 확정될 때 추가한다. 결제계좌 조회·매핑이나 활용현황 집계 API는 필요하지 않다. 실제 endpoint와 필드 구조는 후속 설계 대상이다.

## Acceptance Criteria

- [ ] 카드 탭의 등록 버튼 문구와 실제 이동 대상이 카드 등록으로 일치한다.
- [ ] 계좌를 등록하지 않아도 카드 등록으로 진입할 수 있다.
- [ ] 검색·필터·페이지와 Desktop/Mobile 조회 결과·권한이 일치한다.
- [ ] 명의 설정, 결제계좌 연결, 활용현황 UI가 없다.
- [ ] 비활성 카드의 과거 거래·실적 참조를 보존한다.
- [ ] 사용액 미확인과 실제 0원을 구분한다.
- [ ] Empty / No Result / Loading / Error / Permission Denied를 검증한다.

위 항목은 이전 전체 제품 초안의 기준이다. 이번 샘플 구현의 동작/검증 범위는 아래 v2 계약과 run별 증적으로 구분하며 전체 제품 완료를 의미하지 않는다.
