# 시장가격 이력 및 투자 성과 분석 후속 작업

> 상태: Future / Backlog
>
> 현재 구현 범위: 제외
>
> 문서 목적: 장기 투자 성과 분석을 위해 향후 필요한 시장가격 이력, 포트폴리오 시계열, 성과 지표 및 데이터 공급자 연동 요구를 미리 기록한다. 이 문서는 현재 논리 데이터 모델 또는 API 구현 승인이 아니며, 실제 개발 시 별도 DESIGN 및 데이터 모델 승인을 거쳐야 한다.

## 1. 배경

현재 차곡 투자 모델은 현재 보유정보, 투자금 투입, 실제 현금흐름, 제안/실행 결과, 시점 평가값과 최신 시장가격 관측을 관리하는 것을 우선한다.

현재 `market_price_snapshot`은 단일 공급자의 `(security_id, price_as_of_at)`별 최신 성공 관측값을 보존하며, 동일 기준시각 재수집 시 가격과 조회시각을 갱신한다. 모든 재수집 전 값 또는 장기간의 시장가격 시계열을 분석용 원장으로 보존하는 계약은 현재 범위에 포함하지 않는다.

향후 다음 질문에 답하려면 현재 상태 데이터만으로는 부족하다.

- 내 투자전략의 장기 성과는 단순 지수 투자와 비교해 어떠했는가?
- 가장 크게 하락했던 구간과 하락 폭은 어느 정도였는가?
- 감수한 가격 변동에 비해 장기 수익은 효율적이었는가?
- 어떤 자산이 전체 수익에 기여하거나 하락을 완화했는가?
- 서로 다른 자산이 실제로 분산 효과를 제공했는가?
- 리밸런싱이 단순 보유 대비 성과와 위험에 어떤 영향을 주었는가?

이 기능들은 현재 개발 범위에 즉시 추가하지 않고 후속 분석 기능으로 관리한다.

## 2. 향후 제공할 사용자 기능

전문 투자지표를 그대로 전면 노출하기보다 일반 사용자가 이해할 수 있는 표현을 기본 UI로 사용한다.

| 내부 분석 개념 | 기본 사용자 표현 | 설명 |
|---|---|---|
| CAGR | 연평균 성장률 | 투자기간의 복리 성장 속도 |
| MDD | 최대 하락폭 | 과거 최고점에서 가장 크게 감소한 비율 |
| Sharpe Ratio | 위험 대비 수익 효율 | 가격 변동을 감수한 만큼의 수익 효율 |
| Return Contribution | 수익 기여도 | 각 자산이 전체 수익에 기여한 정도 |
| Risk/Volatility Contribution | 변동성 영향 | 각 자산이 포트폴리오 변동성을 높이거나 낮춘 정도 |
| Correlation | 함께 움직이는 정도 | 자산 간 가격 움직임의 유사성 |

전문 명칭과 계산값은 상세 분석 화면에서 함께 제공할 수 있으나, 기본 화면은 의미 중심의 설명을 우선한다.

## 3. 필요한 원천 데이터

### 3.1 시장가격 시계열

향후 종목별 과거 시장가격을 거래일 단위로 조회할 수 있어야 한다.

개념 예시:

```text
market_price_history
- security_id
- trade_date
- close_price
- adjusted_price 또는 total-return 계산에 필요한 보정 정보
- source
- source_symbol
- fetched_at
```

위 구조는 예시이며 현재 canonical DBML에 추가하지 않는다. 실제 컬럼, 키, 보존기간, 공급자 정책은 후속 DESIGN에서 결정한다.

가격 데이터는 사용자별로 중복 저장하지 않고 종목별 공용 데이터로 관리하는 것을 기본 방향으로 한다.

### 3.2 실제 투자 현금흐름

기존 `investment_cash_flow`를 활용하여 외부 자금 유입/회수와 내부 이동을 구분한다.

XIRR 등 자금가중 성과 계산에서는 ETF 매수/매도를 외부 현금흐름으로 중복 계산하지 않는다.

### 3.3 과거 포트폴리오 평가값

기존 `investment_valuation_snapshot`은 시점 평가를 보존한다.

향후 MDD, 기간별 성과 차트, 위험 분석의 조회 빈도가 높아질 경우 거래일별 포트폴리오 총 평가값을 캐시성 스냅샷으로 별도 관리하는 방안을 검토한다.

개념 예시:

```text
portfolio_daily_snapshot
- portfolio/account scope
- trading_date
- securities_value
- cash_balance
- total_value
- net_external_cash_flow
```

이 데이터 역시 현재 모델에는 추가하지 않는다.

종목별 일별 포트폴리오 스냅샷은 데이터 중복이 커질 수 있으므로 초기 도입 대상에서 제외하고, 거래 이력과 공용 시장가격을 이용해 필요 시 계산하는 것을 우선 검토한다.

## 4. 시장가격 데이터 공급자 후보

### 4.1 국내 ETF

우선 후보는 KRX OPEN API다.

검토 대상:
- ETF 일별매매정보
- 종목 기준정보
- 지수 데이터
- 데이터 제공 가능 기간
- 호출량/인증/승인 정책
- 서비스 배포 및 재사용 시 이용약관

국내 ETF가 최초 등록될 때 상장 이후 가능한 범위의 과거 가격을 backfill하고, 이후 거래일마다 증분 수집하는 방식을 우선 검토한다.

```text
종목 등록
  -> 기존 가격이력 확인
  -> 부족한 과거 구간 backfill
  -> 이후 거래일 장 마감 후 증분 수집
```

### 4.2 공공데이터포털

금융위원회/한국거래소 관련 시세·지수·일반상품 API를 보조 공급자 후보로 검토한다.

공공 API라는 이유만으로 자유로운 재배포가 허용된다고 가정하지 않는다. 데이터별 이용허락 조건, 상업적 이용, 변경·재배포 제한을 실제 서비스 전 반드시 확인한다.

### 4.3 장기 백테스트

국내 ETF의 상장일보다 이전 기간을 분석하려면 국내 ETF 가격만으로는 충분하지 않다.

20년 이상 장기 백테스트는 다음을 별도 분석 데이터로 취급한다.

- 기초지수
- 해외 ETF
- 자산군 proxy
- Total Return 지수

실제 보유 ETF 성과와 장기 전략 proxy 결과를 동일한 사실로 표시하지 않는다.

## 5. 가격 데이터와 Total Return

단순 종가만으로 장기 투자성과를 계산하면 ETF 분배금 때문에 실제 투자성과와 차이가 발생할 수 있다.

향후 다음 중 하나를 지원해야 한다.

1. 분배금 반영 수정가격(adjusted price)을 확보한다.
2. 분배금 이력을 별도로 저장하고 Total Return을 계산한다.
3. 공식 Total Return 지수를 벤치마크로 사용한다.

현재 평가액과 단기 가격변동 분석은 종가로 계산할 수 있지만, 장기 CAGR·벤치마크 비교에는 Total Return 기준을 우선한다.

## 6. 저장 용량 및 보존 방향

시장가격은 사용자별 데이터가 아니라 종목별 공용 데이터이므로 거래일 일봉을 장기간 저장해도 초기 차곡 규모에서는 과도한 데이터 증가로 보지 않는다.

예시:

```text
10종목 x 연 250거래일 x 20년 = 약 50,000행
100종목 x 연 250거래일 x 20년 = 약 500,000행
```

반대로 사용자 × 종목 × 거래일 단위의 평가 스냅샷은 대규모 중복이 발생할 수 있으므로 기본 저장 모델로 채택하지 않는다.

기본 방향:

- 시장가격: 종목별 거래일 단위 공용 이력
- 거래/현금흐름: 실제 사건 발생 시 저장
- 현재 보유: 현재 상태 유지
- 포트폴리오 평가 스냅샷: 성능 요구가 확인된 범위에서 저장
- 종목별 사용자 일별 스냅샷: 초기에는 미도입
- CAGR/MDD/Sharpe 자체의 일별 이력: 별도 저장하지 않고 원천 데이터에서 계산

장기 운영 후 데이터 규모가 실제 문제가 될 때 파티셔닝, 압축, 오래된 데이터의 주/월 단위 downsampling 등을 별도 검토한다.

## 7. 계산 기능 후보

원천 데이터가 준비되면 다음 분석을 단계적으로 제공할 수 있다.

### 7.1 우선순위 높음

- 기간별 총 수익률
- XIRR
- 연평균 성장률(CAGR)
- 최대 하락폭(MDD)
- 벤치마크 비교
- 목표비중 대비 현재비중 및 리밸런싱 효과

### 7.2 후속 고급 분석

- 위험 대비 수익 효율(Sharpe Ratio)
- 자산별 수익 기여도
- 자산별 변동성/위험 기여도
- 자산 간 상관관계
- 리밸런싱 기여 효과
- 시장 국면별(regime) 성과 비교

고급 지표는 계산 엔진에서는 정식 정의를 사용하되, UI에서는 일반 사용자가 의미를 이해할 수 있는 표현을 우선한다.

## 8. 현재 모델과의 관계

현재 canonical 모델의 다음 책임은 유지한다.

- `investment_cash_flow`: 실제 외부 입출금/내부 이동 사건
- `investment_valuation_snapshot`: 계좌별 기준시점 평가 이력
- `market_price_snapshot`: 단일 공급자의 종목·기준시각별 최신 성공 관측값
- `investment_holding`: 현재 보유 상태

이 문서의 `market_price_history`, `portfolio_daily_snapshot` 등은 향후 검토용 개념명이며 현재 승인된 테이블이 아니다.

후속 작업에서 기존 snapshot 책임을 확장할지, 별도 history 테이블을 추가할지 먼저 데이터 모델링을 수행해야 한다. 같은 의미의 데이터를 중복 source of truth로 만들지 않는다.

## 9. 후속 작업 시작 조건

다음 중 하나 이상이 실제 제품 요구로 확정되면 본 문서를 후속 작업의 입력으로 사용한다.

- 1년 이상 기간의 투자 성과 차트 제공
- 최대 하락폭 또는 위험 대비 성과 제공
- 자산별 수익/방어 기여도 제공
- S&P500 등 벤치마크와 장기간 비교
- 리밸런싱 효과 분석
- 사용자 보유 전 기간의 자동 백테스트
- 시장가격 데이터를 반복 외부 호출하지 않고 내부에서 재사용할 필요 발생

## 10. 후속 작업 체크리스트

실제 구현을 시작할 때 다음 순서로 진행한다.

- [ ] 분석 기능의 제품 범위와 사용자 표현 확정
- [ ] 필요한 지표별 정확한 계산 정의 확정
- [ ] KRX 및 공공 API의 실제 제공 데이터·기간·호출 제한 재검증
- [ ] 데이터 이용약관 및 서비스 재배포 가능 범위 확인
- [ ] 분배금/수정주가/Total Return 처리 정책 결정
- [ ] 시장가격 공급자 추상화 및 fallback 필요성 검토
- [ ] 가격 이력 backfill 및 일별 증분 수집 정책 설계
- [ ] 기존 market_price_snapshot과 history 책임 경계 재설계
- [ ] 포트폴리오 일별 스냅샷 도입 필요성을 성능 기준으로 결정
- [ ] canonical DBML 변경 시 별도 Data Model Gate 승인
- [ ] 성과 계산 회귀 테스트 및 벤치마크 대조 데이터 마련
- [ ] UI에서는 전문용어보다 사용자 친화적 설명을 기본으로 제공

## 11. 현재 비범위

이 문서를 추가하는 시점에는 다음 작업을 수행하지 않는다.

- canonical `schema.dbml` 변경
- `investment-model.md`의 승인 데이터 계약 변경
- 시장가격 수집 배치 구현
- KRX/Open API 연동 구현
- 과거 가격 backfill 실행
- CAGR/MDD/Sharpe/기여도 계산 코드 구현
- 투자 분석 화면 추가
- 기존 `market_price_snapshot` 보존정책 변경

즉 본 문서는 **향후 분석 기능을 위한 작업 예약 및 설계 메모**이며 현재 개발 범위를 확장하지 않는다.
